## 2. Formats (frozen for Phase 2; schema number 0)
**`<id>.ftplugin`** = zip, deterministic (sorted entries, fixed timestamps). `manifest.json` lists a SHA-256 for every other file; `pack` refuses a damaged file.
**`registry.json`** (written by `pack`, read by the server): plugins, blocks (`model`, item configuration), items (`base`, `item_model`), paintings (`asset_id`), `retired_blocks`, `pack_format`.
**`allocations.json`** persists known block IDs and retirement status. Existing carrier-slot files are migrated to retained IDs and the unused slots are dropped.
**`pack.zip` + `pack.sha1` + `pack.json`**: SHA-1 of the exact bytes served (this is what the client checks). `versions.toml` stores `resource_pack_format = [major, minor]`; `pack.mcmeta` writes that exact tuple to both `min_format` and `max_format` (26.3: `[97, 1]`).

### Hard invariants (do not break; they protect worlds)
1. **Saved worlds store namespaced ids (`example:bait_crate`), never carrier states.** Chunk PDC records are the source of truth. A barrier is the collision/selection block; the client sees an item-display entity whose stack uses the same `item_model` as the block item. A matching interaction entity relays clicks to `FlowTailBlockInteractEvent`.
2. Unknown ids (plugin removed) are **preserved**, never turned into air (`/content missing` reports them; P3-10).
3. Carrier slots are append-only (above).
4. The compiler never writes into the server world or accepts the EULA.

## 3. Add-only cube projections (ADR-024)
Vanilla note blocks and every other vanilla block retain their normal behaviour. The generated pack adds namespace-owned item models only; it does not add or replace files under `assets/minecraft/blockstates/` or `assets/minecraft/models/block/`. The server saves `x,y,z → namespaced id` in chunk PDC, places a barrier at each known FlowTail block, and spawns a persistent item display plus interaction entity. Their entity PDC records the projected coordinates so missing entities can be rebuilt when a chunk loads and stale entities removed. Player-placed barriers have no FlowTail record and remain ordinary barriers.

On chunk load, records made by the old note-block carrier are migrated only at recorded positions to barriers. This leaves unrecorded vanilla note blocks untouched. Records for removed plugins are retained and projected with a placeholder. Mining hardness/tools and real survival mining are P3-04; entity projection has additional entity cost, no block-light emission parity, and unverified Geyser behavior.

**Projection geometry (ADR-025, `ProjectionSpec`).** The display uses item-display context `NONE` (no display transform) at scale 1.002, so a cube fills exactly one block and its faces do not z-fight with neighbours. Context `FIXED` was the first build: vanilla block models carry an item-frame `fixed` transform of scale 0.5, which made every custom block half size (found 2026-11-22 from a screenshot of Bait Crate). The interaction entity is spawned at the block's base centre (its box grows upward from the entity's feet; spawning at the block centre had shifted it up half a block) and is 0.98 wide/high, a little smaller than the block, so the barrier stays the client's click target and every vanilla item places against a FlowTail block as it would against stone. `ProjectionSpec.LAYOUT` is stored in each entity's PDC state (`flowtail:projection_state`); on chunk load a projection whose stored state differs (old layout, plugin added/removed since, duplicated entities) is rebuilt, and entities that no record owns are removed (never when a chunk has unreadable records).

**Interim survival breaking.** Barrier cannot be mined in survival, so until P3-04 a survival left-click on a FlowTail block (`PlayerInteractEvent` LEFT_CLICK_BLOCK) or on its interaction entity (`PrePlayerAttackEntityEvent`) breaks it next tick through a normal `BlockBreakEvent` (protection plugins can veto), dropping the block item (nothing if `item.auto=false` or the plugin is missing). Creative uses the client's own instant break. Break plays the block's `sounds.preset` break sound and item-crumb particles from its own model.

**Base-item leakage (found 2026-11-21).** A custom item is a vanilla base item underneath (River Fish is `paper`, blocks use `paper` by default), so vanilla recipes and machines see the base item: Ruby + gunpowder crafted a firework rocket. `VanillaRecipeGuard` blocks crafting, smelting and fuel use for custom items unless the recipe key is in the `flowtail` namespace (P3-08 recipes). Still open: smithing, anvil, brewing, composting, villager trades, dispensers, creative middle-click. **Block items** are auto-generated from each block (`item.auto`): base `minecraft:paper` by default (`item.base` overrides), `item_model` = the block id; placing one writes the barrier hitbox and id to chunk PDC and adds its entities.

**FlowTail menu (ADR-021).** Creative tabs cannot be extended from the server, so custom items are offered by a menu: `MenuDialogs` (bootstrap) registers dialog `flowtail:menu` and tags it `minecraft:pause_screen_additions`; its external title is the gradient label. Its one button sends custom click `flowtail:menu/custom_items`; `CustomItemsMenu` receives `PlayerCustomClickEvent` (player via `PlayerGameConnection#getPlayer`) and opens a 54-slot chest menu (45 items per page, previous/close/next on the bottom row; click = 1, shift- or right-click = full stack; every click in the menu is cancelled). `/flowtail` opens the same menu if the pause button is unavailable. Settings: `menu.enabled`, `menu.label`, `menu.color.from`, `menu.color.to`, `menu.bold`, `menu.custom-items.label`, `menu.custom-items.title`, `menu.custom-items.access` (all restart-required).

## 4. Server side: design grounded in Paper's API (read from source at commit 1eda666, not yet compiled against)
Paper already exposes what we need for the MVP, so **Phase 2 does not need deep NMS patches**; build it as a bundled system plugin/module (`content-engine/`) first, move hot paths into patches in Phase 4.

**Step 0 API correction (2026-11-21):** Paper 26.3's `RegistryEvents` exposes a compose event for `PAINTING_VARIANT`, but it does not expose custom `BLOCK` or `ITEM` registry events. Blocks and items are FlowTail definitions stored in the internal content registry; block projections use entities plus a barrier hitbox. Only painting variants are added to a real Minecraft registry through Paper's registry compose API.

| Need | Paper API found | Notes |
|---|---|---|
| Load FlowTail definitions early | `io.papermc.paper.plugin.bootstrap.PluginBootstrap#bootstrap(BootstrapContext)` | P2-01 loads and validates `registry.json` before normal plugin enable |
| Painting variants | `RegistryEvents.PAINTING_VARIANT.compose()` + `PaintingVariantRegistryEntry.Builder` (`width`, `height`, `assetId`, `title`, `author`; width/height 1–16) | Experimental real-registry API; use for P2-01 painting registration |
| Blocks/items | No Paper 26.3 custom BLOCK or ITEM registration event | Keep FlowTail definitions; project blocks with barrier + item display + interaction entity |
| Item model | `DataComponentTypes.ITEM_MODEL` (value is a `Key`) | `item_model` = `example:river_fish` |
| Stored item id | no `custom_data` constant in `DataComponentTypes`; use the item's `PersistentDataContainer` (stored inside `custom_data`) | key `flowtail:id` |
| Send pack | `Player#setResourcePack(UUID, url, hash, prompt, required)`, `PlayerResourcePackStatusEvent.Status` (`SUCCESSFULLY_LOADED, DECLINED, FAILED_DOWNLOAD, INVALID_URL, FAILED_RELOAD, DISCARDED…`) | implemented in P2-07; declined required pack follows `pack.decline-action` |
| Configuration-phase hold | `AsyncPlayerConnectionConfigureEvent`, `PlayerConnectionInitialConfigureEvent` | These events do not expose a way to suspend configuration until pack status; P2-07 uses join-time request and freezes movement until `SUCCESSFULLY_LOADED` |
| Per-chunk storage | chunk `PersistentDataContainer` | VERIFY the exact interface; store `local x,y,z → namespaced id` |
| Block/entity events | `BlockPlaceEvent`, `BlockBreakEvent`, `PlayerInteractEntityEvent`, `ChunkLoadEvent` | Persistent entity projection backed by chunk records |
| Pack host | JDK `com.sun.net.httpserver.HttpServer` | no dependency; verify SHA-1 at startup |

Pipeline at server start (P2-01/P2-07): read `content-state/plugins/*.ftplugin` → run the Java pack step (port of `compiler/ftc/pack.py`; golden-tested by ZIP entry hashes) → write `registry.json`, `allocations.json`, `pack.zip` → verify and start host → register content → on join send pack and hold required-pack players until status. `pack.required=false` sends an optional pack without a movement hold. `limbo-lag` uses a hidden, invulnerable low-chunk limbo per ADR-016's implementation note; it does not delay keep-alive packets.

## 5. Why the compiler is Python now and what happens to it
Python is quick to build and test here, and matches `parity/flowtail.py`. But the server must merge packs at start (Q5a) and end users should not need Python. **Proposed ADR-018:** the Python compiler is the *reference implementation*; the server gets a Java port of `pack` (and later `build`) checked against **golden vectors**: for the same `.ftplugin` inputs both produce identical `registry.json`, `allocations.json` and identical per-entry contents of `pack.zip` (compare entry hashes, not zip bytes). Add `compiler/tests/golden/` when the Java port starts. If you prefer one implementation, port everything to Java and keep this Python code only as test oracle — tell Claude/Codex which.

## 6. Phase 2 acceptance test (manual, vanilla 26.3 client)
0. **Fastest path: `bash scripts/test-all.sh`.** It runs the Python tests, builds the content, builds the server (which runs the Java unit tests), boots it, types `content selftest` into the console, stops it, and writes `build/test-all/REPORT.txt` to paste back (`--quick` = Python + content only, `--no-server` = no boot, `--bots` = also connect 3 idle bots). The manual steps below are what it cannot do.
0. **Self-test by hand (server side, one command).** With the server running, type `content selftest` in the server console (the console needs no slash) or `/content selftest` in game as an op. It places a few temporary blocks next to you (or the world spawn for the console), runs the server-side checks and removes them again in the same tick. Every line is `PASS`, `FAIL` or `SKIP` (a skip is never counted as a pass) and the last line is `SELFTEST PASSED|FAILED: N passed, N failed, N skipped`. Paste that block back when something fails. It checks, for every registered item: reverse mapping, save/load, that `expand()` keeps enchantments and damage, and (in game only) the real `InventoryCreativeEvent` path with and without the id tag; and for the first registered block: placement, projection (1 display + 1 interaction, right model, exact size and alignment, click box), saved id read back after dropping the cache, self-heal of a missing display, duplicate cleanup, a block removed behind our back (WorldEdit style), the break path, an unknown-plugin placeholder that is kept, vanilla note blocks and player barriers left alone, and a chunk unload/reload when the server allows it. It cannot prove anything a client draws: steps 2 to 5 below stay manual.
1. `bash scripts/gen-reports.sh && bash scripts/build-content.sh` → no errors; only the known stairs warning.
2. Start FlowTail with the example plugin installed. Join with a vanilla client: accept the pack. Decline it once: see the "unplayable" message (pack.decline-action).
3. `/give @s example:river_fish` → inventory shows the fish texture, not paper. Use the Custom Items menu or `/give @s example:bait_crate`, place Bait Crate, and verify its display-entity texture, barrier collision, and click event. Verify vanilla note blocks still place, tune, and play normally. The crate must fill its whole outline (not half size) and the outline must match the crate. Survival: left-click breaks it instantly and the item drops (hardness and tools are P3-04); creative break cleans up the projection and saved id. Right-click with cobblestone, stairs and a torch places them against the crate normally; `/content inspect` on the crate prints `display=1 interaction=1 ... (healthy)`.
4. Stop/start the server: Bait Crate blocks and their projections return. Remove the plugin: world loads, saved IDs remain and render placeholders; `/content missing` lists `example:bait_crate`. Re-add: the Bait Crate projection returns. For a pre-ADR-024 world, verify only recorded FlowTail note-block positions migrate to barriers while ordinary note blocks remain unchanged.
5. Bot swarm (tools/bench) still logs in and reports MSPT; no new errors in the structured log.

## 7. Shape templates (P3-01, ADR-024/030): add-only server and client checks

Build and start with both example plugins (`bash scripts/build-content.sh` now builds both; `bash scripts/test-all.sh` runs the server checks). The console self-test verifies each registered template has a barrier hitbox, saved id/state, a matching item-display variant, one interaction entity, state updates, projection repair and cleanup. It does not verify client appearance or partial collision.

Every template uses a FlowTail barrier at its recorded position. Vanilla blocks are not used as runtime carriers. The item display draws the authored shape, while the current collision/selection hitbox remains a full cube. FlowTail stores template state in the chunk record; old carrier states are converted only when the same position has an existing FlowTail id record. Unrecorded vanilla blocks are left alone.

The vanilla-client checklist remains needed to accept P3-01. It checks appearance, item use against custom blocks, orientation, custom mining, restart persistence and absence of vanilla block changes. It must not expect partial collision, redstone output, shelf inventory, or waterlogging until those are implemented in FlowTail itself. In particular, the current trapdoor/button state is visual state only and the shelf has no storage API yet. The user selected server-side verification only for this pass, so client acceptance is intentionally open.

For a client check when available, give `/give @s shapes:weave_slab` (and `weave_stairs`, `weave_hatch`, `weave_button`, `weave_plate`, `weave_mat`, `reed_tuft`, `weave_shelf`). Textures include a red “L” for orientation. Confirm the visible model, item placement, timed mining, and restart persistence. Use F3+B to confirm that the current full-cube hitbox is understood as a known limitation rather than mistaken for shape collision. Test that ordinary vanilla slabs, stairs, shelves, trapdoors, buttons, pressure plates and carpets placed elsewhere retain their normal state and behavior.
